## 4. Evidence so far (synthetic graph, 2-core sandbox)

* Oracle vs brute-force path enumeration (time, distance, full Pareto front): 36 queries, 0 mismatches.
* C++ (sequential, parallel with 1 to 16 threads, 3 list types) vs an independent Dijkstra and vs the Python golden file: about 850,000 checks, 0 failures, at 96 and 288 time buckets; a golden file from different inputs is rejected.
* Mutation checks of the test suite: early decrement of the pending counter → hang, caught by the watchdog; plain store instead of CAS-min → caught by the dedicated hammer test (5/5 runs on an idle machine, 0/3 while another heavy process shared the two cores — detection is timing-sensitive, so TSan and the Apple M3 run matter); removing the stale check → still correct (it is only an optimisation).
* ThreadSanitizer (g++, x86-64, 2 cores): 850,900 checks, 0 failures, no race reports, including the 48k-node stress graph (about 7 min). An earlier TSan run that took more than 10 minutes was a bug in my test (threads busy-spinning on a start flag without yielding starve each other when threads outnumber cores); fixed, and the per-stage timing printed by the test makes a slow stage visible immediately.
* **Finding: FIFO lock convoy.** With the real A1 `lock_ticket`, the stress test (16 threads, 2 cores) took 188 s versus 11.5 s with the TTAS lock and 16 s with `std::mutex`, even without TSan; under TSan the gap is larger. Results were correct. Cause: a ticket lock must serve waiters in order, so when the next ticket holder is descheduled (threads > cores) everybody else spins 2048 iterations then yields, in vain. Consequence for the experiments: thread counts above the core count must be tagged as oversubscribed, and a FIFO lock should not be expected to scale there; `std::mutex` is a useful baseline. The tests now keep FIFO-lock runs at or below the core count (other locks still run up to 16 threads). My first sandbox runs used a simplified stand-in lock that yielded immediately and so hid this effect.
* Group machine (Đạt's laptop, WSL2, real A1 `lock.h`; first build against the real header): `run_tests.sh` passed (850,900 checks, 0 failures) and `make test-tsan` / `make test-tsan-stress` ended with 0 failures. That run used the older test version that did not cap FIFO locks: its ticket-lock stress stage took 1738.7 s under TSan (versus 116.2 s for TTAS), and 38.8 s versus 7.9 s without TSan, which confirms the convoy finding on a second machine. The newer tests cap this.
* **First real-graph pilot (Ryzen laptop, WSL2, 195,823 nodes, coarse-locked list; planning numbers only).** Sequential median per query by distance bin: 0.21, 0.82, 3.6, 9.4, 15.5 ms; only bin 0 (1-3 km) is below the 20 ms batch floor with 50 pairs. Parallel A* was slower than sequential everywhere and got slower with more threads: time relative to sequential 2.3x at 1 thread, 3.5x at 2, 5.4x at 4, 6.4x at 8 (TTAS list); 2.7x to 9.5x for the ticket lock; 2.4x to 18.4x for `std::mutex`. So there is no speedup with the single-lock list, even relative to the same code at 1 thread. A synthetic diagnostic run (`tools/summarize.py`) shows the same node expansions in sequential and parallel runs and about 9x higher list-insert latency at 2 threads than at 1, which points at the lock and the sorted list rather than extra search work; the real-graph diagnostic (18 Nov, below) confirms it. Per-node work in A* is tiny compared with a lock round trip, so a shared single-lock list cannot scale; ideas to test once the Section-2 lists exist are in `TASKS.md` (row 18).
* **Diagnostic on the real graph (Ryzen laptop, WSL2, 3 repetitions, `--latency`, planning numbers).** (1) Correctness: C++ results equal the Python golden files on all 5,000 time rows (seq, par x 1/2/4 threads, `coarse_std_mutex`) and on 500 distance rows; 0 mismatches, all paths verified. (2) No extra search work: expansions per query are identical in sequential and 1-thread/2-thread parallel runs (e.g. bin 4: 92,023) and rise by under 0.02% at 4 threads; reopenings stay under 0.3%. (3) Two separate costs explain the slowdown. *Data structure:* the sequential baseline uses a binary heap, the parallel code a sorted linked list whose insert is O(open-list length). With 1 thread and no contention the parallel code is already 0.89x, 0.58x, 0.45x, 0.26x, 0.22x of sequential speed on bins 0-4: it degrades as queries get longer because the frontier grows; mean insert latency rises from 75 ns (bin 0) to 555 ns (bin 4) while pop-min stays at the timer floor (about 27 ns). List operations take 55% of search time at 1 thread in bin 0 and 86% in bin 4. *Lock contention:* summed list-operation time per query is about 2x the wall time at 2 threads and 4x at 4 threads, so every thread spends essentially all its time inside list operations (mostly waiting for the lock); pop latency grows from 27 ns to 2,030 ns at 4 threads in bin 4. Speedup relative to the same list at 1 thread is 0.57-0.81 at 2 threads and 0.42-0.54 at 4 threads. `std::mutex` at 2 threads is 4-5x slower than the TTAS lock (futex sleep/wake costs more than the very short critical section). Consequence for the study: the Section-2 lists, not the search code, decide Section-3 scalability, and the comparison must include a sequential version with the same sorted list so that data-structure cost and synchronisation cost are reported separately.
* **Vector (Pareto) A* (synthetic graph, 18 Nov).** `include/astar/pareto.h`. Tests: fronts equal an independent label-correcting reference (30 queries, 24 with multi-point fronts) and the Python Martins oracle (24 queries, exact mode; 0 mismatches; seq, par 1/2/4 threads, 3 lists); 2,426 checks with the 48k-node stress graph, 0 failures; ThreadSanitizer on the small graph: 2,232 checks, no race report. Mutation checks: pruning on time only, removing eviction, dropping the dominance test and removing the node lock are all caught; replacing weak by strict dominance survives because it only adds equal duplicates (behaviourally equivalent). Relaxed mode (noise 250 permille, inflation 130%): paths valid, nothing better than the exact front, hypervolume ratio 0.97 on average (minimum 0.72). **Performance finding:** with the sorted-list open list the parallel vector search is far slower than the sequential one with identical work: one 25 km query on the 48k-node graph creates 356k labels, 0.35 s sequential (binary heap), 18.5 s parallel at 1 thread and 19-21 s at 2-16 threads. Vector search keeps a very large open list and a sorted-list insert costs O(list length), so the list, not the locks, dominates; the report must say this and the Section-2 lists (fine-grained, lazy) will not change it much unless the traversal is shortened.
* **Scalar experiment run on the real graph (Ryzen 5 6600H, 6 cores / 12 threads, WSL2; 103 configurations, 10 repetitions, shuffled).** All exact configurations matched the golden files. Pinned and unpinned runs are about equal. Heuristic sensitivity: inflation 150% cuts expansions by 44% at 0.2% mean gap; noise raises expansions and gap.

* **List insert profile (19 Nov, synthetic 48k-node graph, plain `coarse_ttas`, 1 thread; `--list-profile`, file `<out>.listprof.csv`).** Mean steps per insert are 80% of the list length at insert time (for example scalar bin 4: 495 steps at mean length 699; vector bin 1: 316-332 steps at length 407-422). Inserts land late in the list: about 30-45% in the last eighth and about 70% in the last three eighths, 3-5% in the first two. With the windowed list the mean walk is 0 steps and the mean list length 0.3-6 items. **The real graph (Ryzen laptop, WSL2, 1 thread, plain `coarse_ttas`) behaves differently from the synthetic one:** the mean walk is 51-54% of the list length in every bin (scalar bin 0: 53 steps at length 98; bin 4: 415 steps at length 806, max length 2,008; vector bin 0: 126 at 236; vector bin 1: 386 at 747, max 2,076), and inserts land roughly bell-shaped around the middle (6-7% in the first eighth, 15-16% in the middle eighths, 9-10% in the last; 18% in the first two eighths, 37-40% in the last three). So the O(length) walk is measured on the real data, and the synthetic 'inserts land near the tail' result does not transfer. Consequence: a tail pointer would help little; searching from the nearer end of a doubly linked list would at best halve the walk. Only shortening the list (windowing, better pruning, a stronger heuristic) removes it. Vector bins 2-3, where the smoke run spent its time, were not profiled.

* **Vector stall diagnosis and fix (real graph, Ryzen laptop, WSL2, 6 threads, 20-21 Nov).** Symptom: on some bin-4 repetitions at batch >= 12 a query took 1-14 s instead of 0.4 s (query 404 under `win_coarse_ttas`: 11 of 30 repetitions slow at batch 12, 1 of 30 at batch 8), with the same results. Instrumented runs (`--diag`, file `<out>.diag.csv`) show: slow and fast repetitions do the same work (identical expansions, list adds and lock acquisitions); no idle time at the end, no work hoarded in prefetch buffers, and no descheduled lock holder (lock holds of 1 ms or more are essentially absent); but the shared list was about 1,850 items long instead of about 105, so a lock hold took 17 us instead of 0.9 us and the lock was busy about 90% of the time (threads serialised, 70% of thread time waiting). Slow repetitions had 6x more direct inserts into the shared list (400k vs 66k): a window advance opened the window around the advancing thread's own smallest bag item, which can sit far above the global smallest (89-98% of advances jumped more than one window, measured with the new advance counters). Tried and rejected: capping the number of items a promotion may move (no effect, 12-16 of 200 repetitions still slow), following the global minimum exactly (the list stays below 2,000 items but threads are 65-98% idle and the search is 2-10x slower, measured on the synthetic graph), starting slack only after a thread took 50,000 or 200,000 items (no protection: 15-20 of 200 slow, because the threshold only moves forward). Kept: slack K (decision 31) and skip-empty. Short searches starve under slack mainly because idle threads lock the empty list on every poll; skip-empty cut the bin-0 cost of slack 16 from 0.9 -> 10 ms per query to 0.9 -> 1.8 ms. Result, bin 4, batch 12, `win_coarse_ttas`, divisor 65536, 200 repetitions per cell: base 503 ms per query mean, 15 slow repetitions, worst 10.1 s; slack 16 + skip-empty 168 ms, 0 slow, worst 0.45 s (all fronts equal to golden). Window sweep with the fix (divisor 16384, 6 threads, 5 repetitions, speedup vs the sequential heap over all bins; slow = repetition more than twice its query's median): `win_coarse_ttas` batch 16: 0.89x without (5 slow, worst repetition 13.5 s), 2.79x with skip-empty only (6 slow, worst 6.4 s), 3.03x with slack 64 + skip-empty (0 slow, worst 2.6 s; bin 0 1.12x, bin 1 1.90x, bin 4 3.10x); batch 12 slack 64 + skip: 2.84x (0 slow); `win_fine_ttas` batch 8: 2.96x with skip-empty only (1 slow, worst 3.0 s), batch 12 slack 64 + skip 2.85x (0 slow, bin 0 1.01x). Scalar search (divisor 4096, 6 threads): skip-empty adds 3-6% (`win_coarse_ttas` batch 8: 1.47x -> 1.54x; batch 16 1.47x -> 1.51x; `win_fine_ttas` batch 16 1.27x -> 1.35x, batch 8 unchanged at 1.25x), slack makes it worse (batch 8: 1.14x at K=64, 0.63x at K=8; bin 0 up to 10x slower), so slack stays off for the scalar search. Limits: one machine, 5-10 repetitions per cell, 6 threads; 12 threads, the other two platforms and the tuned-per-platform settings are not measured yet.

* **Optimistic list inside A* (real graph, Ryzen laptop, WSL2, 6 cores; 26 Nov; exact heuristic, all path checks passed, expansions per query equal to the other lists; speedup vs the sequential heap).** *Plain lists, scalar, bin all, pinned, 6 threads:* `opt_ttas` 0.168, `opt_std_mutex` 0.196, `fine_ttas` 0.186, `coarse_ttas` 0.098; at one thread `opt_ttas` is 0.033 against 0.082 (`fine_ttas`) and 0.235 (`coarse_ttas`), because every operation walks the list twice and locks two nodes. Its efficiency relative to its own one-thread time is the best (0.84 at 6 threads, against 0.38 fine and 0.07 coarse), but it starts from the slowest single thread, so it only ties the fine-grained list in absolute speed; the choice between TTAS and `std::mutex` changed the time by less than 10%. *Windowed, scalar preset:* `win_opt_ttas` is flat, 0.35 / 0.38 / 0.36 / 0.36 / 0.33 at 1 / 2 / 4 / 6 / 12 threads (stalls at 12 threads: 11), against 1.54 (`win_coarse_ttas`) and 1.25 (`win_fine_ttas`) at 6 threads. *Windowed, vector preset:* 0.55 / 0.77 / 1.18 / 1.31 / 1.12 (16 stalls at 12 threads), against 2.84 (coarse) and 2.85 (fine) at 6 threads; it scales (2.4x from 1 to 6 threads) but at about half the speed. Conclusion: the optimistic list is correct and scales well, but it never beats the heap on the scalar search and stays below the coarse and fine windowed lists; it is reported as the Section-2 comparison variant, not as a recommended setting. *Peak memory (whole process, graph included; same run, `peak_rss_kb`):* plain scalar lists 80 MB for the heap, coarse, fine; `opt_ttas` 114-118 MB (+34-38 MB). Windowed scalar at 1 / 6 / 12 threads: `win_coarse_ttas` and `win_fine_ttas` 80 MB, `win_opt_ttas` 114 / 128 / 137 MB. Windowed vector: heap 87 MB, `win_coarse_ttas` 87-99 MB, `win_fine_ttas` 91-104 MB, **`win_opt_ttas` 950-958 MB, about 10x more**, because unlinked nodes are kept until the query ends (decision 33) and the vector search removes very many items. So the memory cost of the design is real and large on the vector search. It does not by itself explain the slow speed: the vector run scales despite using 10x the memory, and the scalar run uses only +34 MB yet stays flat; the flat scalar curve was diagnosed on 27 Nov (`tools/opt_diag.py`, 6 threads, 5 repetitions): not the allocator (jemalloc: `win_opt_ttas` 0.32 -> 0.35, `win_coarse_ttas` 1.34 -> 1.26, inside the run-to-run spread; the same `win_coarse_ttas` cell measured 1.54 in the thread-curve run), not the retired stack (0.000 failed CAS per pop), not the validation walk (shared list about 10 nodes: 9.8 find steps and 10.9 validate steps per attempt; 21-25% of attempts retry). The cost is in `pop_min`: 1,829 ns against 538 ns for `win_coarse_ttas` at 6 threads (209 vs 111 ns at 1 thread), while `add` is equal (51 vs 53 ns). Task 27 (wait counters, second run, 27 Nov): a `pop_min` waits 816 ns for the head lock, 117 ns for the first node's lock and holds the head lock 190 ns (816 = 4.3 x 190: four to five threads queue on the head lock); 34.5% of add/remove attempts have the head or first node as predecessor and wait 296 ns each, so near-head adds contribute but are not the main cause. Main cause: `OptimisticList` has no `pop_batch` / `add_batch`, so `WindowedList` pops item by item (two locks and a retired-stack push each) instead of taking a batch of 8 per lock acquisition (coarse lock wait 1,066 ns per acquisition, about one eighth per item). This matches the earlier sweep: batch 1 gave 0.33-0.53x at 6 threads for the coarse and fine lists, the level of the flat `win_opt_ttas` curve (0.32-0.45x), i.e. the batch-8 preset is in effect not applied to this list. Batch operations were then added (28 Nov: `add_batch` inserts items that fall between the same two nodes under one lock-and-validate round; `pop_batch` takes up to 64 nodes under hand-over-hand locks and retires them with one push; tests against a set model, concurrent test, search tests with batch 4 / 16, TSan and ASan clean); the re-measurement is pending (TASKS A.28), and the numbers above are from before the change. Run-to-run drift is large (heap 1,307 vs 1,788 ms; `win_coarse_ttas` 1.34 / 1.49 / 1.54x; `win_opt_ttas` 0.32 / 0.45x): compare only inside one run. Per-operation latency (ns, add/pop, 1 and 6 threads): coarse_ttas 543/99 and 4911/3642; fine_ttas 1368/38 and 4428/300; opt_ttas 3509/53 and 4396/347; win_coarse 23/111 and 56/525; win_fine 23/123 and 66/382; win_opt 24/209 and 53/1867. Explained (26 Nov): a node is 384 bytes with the TTAS lock (the lock is padded to cache lines) but only 72 bytes with `std::mutex`, so `opt_std_mutex` retires 5x less memory per removal, and peak RSS is the maximum over time, not a sum: the 80 MB floor is the footprint at load time, and a list that adds less than that during search does not raise the peak. Reproduced on the synthetic graph (heap and `coarse_ttas` 27 MB, `opt_ttas` 36-42 MB, `opt_std_mutex` 27-30 MB). So peak RSS cannot resolve list memory below the floor; per-removal sizes above are the better figure for the plain scalar lists.

## 5. Risks and open items

* Real data exists for HCMC and one machine only; the other two machines still need tests, platform inspection and a pilot (see `TASKS.md`, part A). The golden files now agree with the C++ search on the real graph (see the diagnostic below).
* The speed profile is synthetic; the report must say so.
* Windows-native and macOS-specific code (affinity, memory measurement, inspection script) is untested.
* The code has been compiled only against a stand-in for `lock.h`.
* The Pareto search is tested on the synthetic graph only (golden fronts on the real graph pending); the notebook-bug regression tests are optional and not written.
* A real HCMC graph may contain very long edges that trip the FIFO guard (message: "FIFO guard"); the fix is small.
